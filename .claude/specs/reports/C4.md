## 2. C3 requests (commits `9079318` and `15a6c28`)

1. **HTTP/2 variant of the slow-client test.** `TestServer_SlowClientIsDisconnectedOverHTTP2` runs over TLS with `EnableHTTP2` and checks `resp.ProtoMajor == 2`.
   - On my side, the first run closed the session with `reason=client`, not `slow_client`. Your 0.3 s run may have seen the same, which only the close reason tells apart.
   - The variant revealed **a real bug**: the write deadline stayed armed after a successful write. Under HTTP/2, an expired deadline resets the stream even while the handler is idle, so a healthy session with nothing to send for more than 10 s was cut. With a 15 s ping, a 30 s poll interval was enough to trigger it.
   - Fix: the deadline now covers only the write in progress. A write that fails past its deadline counts as `slow_client` under HTTP/2 too, where it surfaces as a reset stream rather than `os.ErrDeadlineExceeded`.
   - Regression test: `TestServer_IdleHTTP2StreamOutlivesTheWriteDeadline`. **It fails without the fix**, which I checked by removing it.
2. **Deadlock guards fail fast.**
   - `within(t, d, fn)` runs the publish loops in a goroutine and fails the test after `d`, instead of hanging the suite. It is used by the frozen-subscriber test and by both slow-client tests.
   - `waitReady` replaces the bare `<-sub.Ready()`.
   - Every stream opened by the server tests now carries a 20 s context, so a stream that never delivers fails instead of blocking.
3. **Timing margins.**
   - The frozen-subscriber bound goes from 250 ms to 2 s.
   - The per-publish bound in the slow-client tests goes from 1 s to 10 s: encoding a ~1 MB snapshot under `-race` on a loaded machine could plausibly cross 1 s, which is my best guess for your unreproducible failure.
   - `Eventually` windows go from 5 s to 10 s.

## 3. Client (`internal/remote/client.go`, 486 lines)

- **`Connect`** runs the handshake and returns a `Session`. Refusals:
  - a protocol other than 1, with the 426 wording of § 5.1: `daemon speaks remote protocol 2, 3, this ember speaks 1: upgrade ember`;
  - 401, as `the daemon refused the credentials (check the token or the client certificate)`;
  - an identity without the `snapshot` scope;
  - an unknown instance, or several instances without `--remote-instance`, both listing the names.
- **`Fetch`** returns each snapshot **exactly once**, in order, and never returns `(nil, nil)`.
  - **With no new snapshot, it waits** until the context deadline, and returns an error once the deadline passes.
  - **While the daemon reports a problem**, it returns that problem immediately:
    - `the daemon cannot reach Caddy since 15:04:05: <error>` for `unreachable`;
    - `the daemon cannot send snapshots since …` for `stale`;
    - `reconnecting to host:port…: <error>` while the stream is down.
  - The TUI calls `Fetch` once per tick, so this does not busy-loop.
- **Deduplication by event id:**
  - After a reconnect, the daemon resends its cached snapshot under the id already seen. The client drops it; otherwise the TUI would compute RPS 0 on that tick.
  - A new epoch in `hello` resets the resume point and calls `OnEpochChange`, the hook PR 2 will use to reset the log buffers.
  - Every `hello` also clears the remembered status, because the daemon only resends a status when it is not `ok`. Without this, an outage would outlive a restart.
- **Reconnection:**
  - Backoff goes 1 s → 2 s → … → 30 s, capped, and resets once a stream was accepted.
  - **A permanent refusal (400, 401, 403, 404, 426) ends the session** instead of retrying (`remote session ended: …`). Retrying a revoked token would trip the daemon's failure limiter after 10 attempts, and the user would then see 429 instead of the real cause.
  - Network errors, EOF, 429 and 503 are retried.
- **Dead stream:** an idle timer is reset on every `Read` of the body, pings included, since the reader drops them. The timer is set to three pings (45 s); when it fires, the request is cancelled and the stream reopened.
- **Declared capabilities:** `Session.Fetcher()` returns a type with `Fetch` only, so the TUI's type assertions find no restart, config or certificate capability. PR 3 will return a richer type there when the handshake announces the capability and the identity has the scope.
- **Unavailability reasons** (§ 7.5):
  - capability absent: `Logs unavailable: the daemon was not started with --remote-logs.`, or `… this daemon does not serve it.` for config and certificates;
  - scope missing: `Logs unavailable: your token lacks the "logs" scope.`;
  - both present: a placeholder for what arrives in PR 2 and PR 3.
- **Token safety:**
  - the client refuses plain `http://` except on loopback (Q2);
  - it never follows redirects (`CheckRedirect`);
  - it trims the token file;
  - no error message contains the token, which the tests assert;
  - `User-Agent: ember/<version>`, which the daemon parses into the `ember_version` audit key.

**Client mode:**
- `--remote` is exclusive with `--daemon`, `--json`, `--expose`, `--stdin-logs`, `--log-listen` and `--remote-listen`.
- `--addr`, `--ca-cert`, `--client-cert`, `--client-key`, `--insecure`, `--interval` and `--frankenphp-pid` are **warned** about and ignored. A malformed `EMBER_ADDR` therefore cannot stop a remote TUI, which is tested.
- The token comes from `--remote-token-file`, otherwise `EMBER_REMOTE_TOKEN`, read only here.
- The TUI interval and FrankenPHP detection come from `Info.instances`.
- Plugins are not provisioned.

**Daemon mode:**
- `--remote-listen` requires `--daemon` and `--remote-auth`.
- It requires `--remote-cert` and `--remote-key` unless `--remote-insecure-plaintext` is set. The two are mutually exclusive, and the plaintext mode logs a warning in full words.
- `--remote-max-sessions` must be at least 1.
- The address must differ from `--expose`.
- `[[client_cert]]` entries without `--remote-client-ca` are a startup error (C2 answer 6).
- TLS is 1.2 minimum. With a client CA, `RequireAndVerifyClientCert` is set.
- `ReadHeaderTimeout` is set and there is no `WriteTimeout`.
- The listener is bound synchronously, so a busy port is a startup error; a later serve error cancels the daemon.
- The single instance is `default` on the wire.

**Environment rule (Q1):**
- A remote variable exported for another mode is **ignored with a warning**, never an error:
  - `EMBER_REMOTE` and `EMBER_REMOTE_INSTANCE` in `--daemon` or `--json` mode;
  - `EMBER_REMOTE_LISTEN`, `…_CERT`, `…_KEY`, `…_CLIENT_CA` and `…_AUTH` outside `--daemon`;
  - any of them on subcommands, silently.
- A flag given on the command line in the wrong mode is an error.

## 8. Questions

1. **Environment rule:** is "ignored with a warning when the variable is exported for another mode, an error when the flag is given on the command line" right? It is the only rule I found that keeps an exported `EMBER_REMOTE` from breaking `ember --daemon` or `--json`, as § 8 requires.
2. **https only:** the client refuses `http://` except on loopback, so the bearer token never crosses a network in clear. It follows that a daemon behind `--remote-insecure-plaintext` is only reachable through its TLS proxy. Agreed?
3. **Daemon interval above 10 s.** The TUI gives each `Fetch` 10 s (`globalFetchTimeout`) and ticks at the daemon's interval. With a 30 s interval, a `Fetch` issued right after a snapshot would time out and show an error for up to 20 s, although nothing is wrong. Options:
   - (a) document intervals of at most 10 s for remote sessions;
   - (b) give the remote fetcher its own wait, the daemon interval plus a margin, by ignoring the TUI's shorter deadline (a small, contained change in the client);
   - (c) raise the TUI timeout in remote mode, which is a `ui` change.

   I lean towards (b). Your call.
4. **Permanent versus retryable statuses:** 400, 401, 403, 404 and 426 end the session; network errors, EOF, 429 and 503 are retried with backoff. Agreed?
5. **Size.** PR 1b is at **1 497** lines outside tests:
   - client 486, broadcast 302, app wiring 313 + 30, server 272, audit +24, UI 69.
   - Together with PR 1a (1 199), PR 1 is about 2 700 lines. That is still for the maintainer (§ 12 Q9), but PR 1b alone is twice the target.

### Answers to your questions

1. **Environment rule: agreed** — a variable exported for another mode is ignored with a warning, a flag given in the wrong mode is an error.
2. **https only, except loopback: agreed.** Say it in `docs/remote.md` (a plaintext daemon is reached through its TLS proxy only).
3. **Daemon interval above 10 s: option (c), not (b).** A `Fetch` that ignores its caller's deadline breaks the `context` contract, and that is what a reviewer will object to. Make the TUI's fetch timeout `max(globalFetchTimeout, 2 × Interval)`. It is one line in `internal/ui`, harmless for local sessions (their interval is ≤ 10 s in practice), and it states the real constraint where it lives. Add a test with a 30 s interval.
4. **Permanent vs retryable: agreed** (400, 401, 403, 404, 426 end the session; network, EOF, 429, 503 retry).
5. **Size: noted for the maintainer.** I will suggest a three-way split in the questions: 1a core, 1b daemon side (broadcast, server, daemon wiring), 1c client and TUI. Do not re-split the branches now.
