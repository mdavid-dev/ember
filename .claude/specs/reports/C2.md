## 2. What C2 adds

### `audit.go`

- There is one method per § 6.5 event: `AuthDenied`, `SessionOpen`, `SessionClose` and `Read`. The message is the event name, every record carries `audit=true`, and the keys are exactly the ones in the § 6.5 table.
- Levels: `WARN` for denied, `INFO` for the rest.
- The event structs have no field that could carry a token, a digest or a config body.
- `user_agent` and `ember_version` are client-supplied, so they are clipped to 256 bytes on a rune boundary.
- Only `remote.auth.denied` is emitted at this checkpoint. The session and read events are defined and tested, and get wired at C3 and PR 3.

### `ratelimit.go`

- The limiter follows § 6.3: 10 failures within one minute block the source for one minute, and a blocked source gets **429 even with a valid token**.
- It tracks at most 10 000 sources, with LRU eviction on the most recent failure. There is no goroutine: expired entries are reset lazily.
- Only authentication failures count. A 403 does not. `Allow` never allocates.
- After a block the count restarts from zero, so one extra failure cannot re-block the source.
- The key is the exact source IP from `RemoteAddr`, in canonical form: IPv4-mapped addresses are unmapped and the zone is dropped. There is no `X-Forwarded-For` (Q8 is still open) and no IPv6 grouping (question below).

### `auth.go`

**Parsing the `--remote-auth` file**

- The file is BurntSushi TOML, and **unknown keys are a hard error**, following the `md.Undecoded()` pattern of `config_file.go`.
- It is refused, with the entry named in the error, for:
  - an unknown scope;
  - empty scopes;
  - a duplicate token name;
  - a duplicate digest;
  - a digest that is not 64 hex characters (a pasted raw token included);
  - an empty, too long or badly charactered name (only `[A-Za-z0-9._@-]`, 1 to 64 characters, since the name reaches logs, the badge and headers);
  - an empty `cn` or a `cn` with control characters, and a duplicate `cn`;
  - a file with no entry at all.
- **Errors never echo a digest.** A TOML syntax error is reduced to `invalid TOML at line N`, and a type error to a fixed message, because BurntSushi errors can quote the offending line. The tests assert that no digest, no digest prefix and no token appears in any error message.
- `expires` must be an **offset date-time**. A TOML local date-time or local date is refused (`expires needs a UTC offset`). BurntSushi marks those with zone names, but only a `toml.Unmarshaler` sees the marker: decoding into `time.Time` silently turns it into UTC or local time. I verified this empirically in the container. `tomlExpiry` does the detection.
- Duplicate scopes are deduplicated and the list is sorted.

**Verification**

- Only one `Authorization: Bearer <token>` header is accepted, with the scheme case-insensitive. Two headers, another scheme or an empty token count as `invalid`.
- The SHA-256 of the presented token is compared with `subtle.ConstantTimeCompare` against **every** entry. There is no early exit and no map lookup by digest, and expiry is checked after the loop.
- The resolution follows § 6.2:
  - A presented token must be valid, and it decides the identity. There is **no fallback to the certificate** when the token is wrong.
  - Otherwise the CN of a **verified** certificate (non-empty `VerifiedChains`) must be declared in `[[client_cert]]`. `ClientCN` is recorded on every path.
- Expiry is exclusive: a token is valid strictly before `expires`.

**Middleware**

- The order is: limiter check, then authentication, then route lookup, then scope check.
- An unauthenticated caller learns nothing about which paths exist: an unknown path gives 401 before authentication and 404 after.
- `routeScopes` is the single table the server will mount (`info` needs authentication only; `stream` needs `snapshot`, `config` needs `config`, `certificates` needs `certificates`).
- Every non-2xx answer uses `ErrorResponse`, with `Content-Type: application/json`, `Cache-Control: no-store` and `nosniff`.
- **401**: the body is always `{"error":"unauthorized"}` with `WWW-Authenticate: Bearer realm="ember-remote"`, and the reason goes to the audit log only (your C1 requirement).
- **403**: `your identity lacks the "<scope>" scope`, as § 7.5 needs.
- **429**: `Retry-After` in seconds, rounded up.

**Reload**

- The identities are held in an `atomic.Pointer[Identities]`.
- `ReloadFile` keeps the current set when the new file is invalid or missing, and returns the error for the caller to log.
- `Revalidate(id)` is the primitive C3 will use to close revoked sessions. It matches the **credential**: digest plus name for a token, CN for a certificate. A token rotated under the same name, a renamed token and a token expired since the session opened all count as revoked. It returns the current scopes.
- The SIGHUP wiring is PR 4, per the § 3 table.

1. **PR 1 split** (§ 6 above): accept PR 1a / PR 1b, or keep one PR over budget?
2. **403 audit.** Keep `remote.auth.denied` / `reason=scope`, and add `identity` to that event, or to every `auth.denied` record, empty when unknown? Or drop the 403 audit?
3. **Audit every 429, or only the transition into the block?** Every 429 follows § 2 item 6 literally. Only the transition bounds the log volume during a flood.

At C3, should a session that loses `snapshot` be closed (`revoked`), and should a lost `logs` scope only stop the log events? That is my proposal.
8. **The CN of an unknown certificate** is not in the audit (the table has no `client_cn` key for `auth.denied`). Should it be added? It helps investigate a stray certificate.

### Review notes

- `authenticate` is right on every point I checked: constant-time scan without early exit, CN read from `VerifiedChains` only, no certificate fallback after a bad token, generic 401, TOML errors that never echo a line.
- **Rate limiter eviction — change required.** Your § 6 says the bypass is inherent to a bounded table; it is not. The flaw is that an entry *still blocked* can be evicted: once blocked, the attacker stops calling `Fail` (its requests stop at `Allow`), so its entry drifts to the back of the LRU and the next fresh failing sources evict it. Required:
  - never evict an entry whose `blockedUntil` is in the future: evict the least recent **unblocked** entry; if every tracked entry is blocked, do not track the new source — or pick another policy of equal strength and say which;
  - key by **/64 for IPv6** (your Q4: yes), exact address for IPv4;
  - a test: block one source, then fail from `capacity` other sources, and assert the first is still refused.
