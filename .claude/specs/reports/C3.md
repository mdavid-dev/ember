## 2. C2 carry-overs (commit `10354c2`)

- **Blocked sources are never evicted.**
  - Blocked entries leave the LRU and move into their own FIFO. Since `blockFor` is constant, that FIFO is ordered by expiry, so expired blocks are dropped from its front in O(expired), lazily, on `Allow` and on `Fail`. A source whose block is over is forgotten and starts afresh.
  - At capacity, the victim is the least recent **unblocked** source. When every tracked source is blocked, the new source is **not tracked**, and the table stays bounded.
  - I chose this over an O(n) scan of the LRU tail, which an attacker could force by getting many sources blocked.
  - Tests:
    - `TestRateLimiter_BlockedSourceIsNeverEvicted` is your case: block one source, fail from `capacity` other sources, and the first one is still refused.
    - `TestRateLimiter_AllBlockedLeavesNewSourcesUntracked` checks that expired blocks free their slots.
    - `TestRateLimiter_EvictsLeastRecentUnblocked` and `TestRateLimiter_FailReportsTheBlockTransition`.
- **IPv6 is keyed by /64**, IPv4 by the exact address, and an IPv4-mapped address stays IPv4. This is `sourceKey`, which replaces `clientIP`. `remote_addr` in the audit keeps the full address; the /64 is only the limiter key. Tests: `TestSourceKey` and `TestMiddleware_RateLimitGroupsIPv6By64`.
- **Answer 2 and answer 8:** every `remote.auth.denied` record carries `identity` and `client_cn`.
  - The verified CN of an unknown certificate is now logged, clipped like the user agent. `authenticate` returns it on every deny path.
  - An expired token names its owner in `identity`.
- **Answer 3:** a 429 is audited once, at the transition into the block, with `reason=rate_limited`, `source` (the limiter key) and `failures`. `Fail` returns whether the failure started a block, and later 429s are not audited.
- Two existing tests were changed rather than extended, because their old assertions encoded the old behaviour:
  - `TestMiddleware_RateLimit` now expects one `rate_limited` record, not two;
  - `TestAudit_EventKeysArePinned` pins both shapes of `auth.denied`, with and without `source`/`failures`.

## 3. `broadcast.go`

- `NewBroadcaster(instances []InstanceSpec, log)` takes the instances under their wire names. The mapping of `""` to `default` is the caller's job at C4. The epoch is drawn with `crypto/rand.Text()` at construction, so every daemon start gets a new one.
- **`PublishSnapshot` never blocks and never keeps the `*Snapshot`.**
  - It encodes on the poll goroutine, before returning, because `model.State` shares `*HostMetrics` pointers with the next poll.
  - It then replaces each subscriber's **pending slot** under that subscriber's mutex and wakes it through a non-blocking send on a capacity-1 channel.
  - A subscriber therefore holds at most one snapshot and one status: **latest wins**, nothing queues, and a slot cleared by `Take` is never resent.
  - `Take` returns the pending events sorted by seq.
- **Status events** are emitted on a change of state only:
  - `unreachable`: from `PublishFailure(instance, err)`, a failed poll, with `error` set to the poll error;
  - `ok`: the next snapshot that gets sent;
  - `stale`: a snapshot that fails to encode (for example a NaN CPU percentage from gopsutil) or exceeds the client bound.
  - `since` is the time of the change. See Q1.
- **Client bound (C1 carry-over):**
  - The daemon checks encoded snapshots against the **same constant** the client reader uses, `DefaultMaxEventSize`. An oversize snapshot is not sent. Instead the stream gets a `stale` status, with an error log when the condition starts and an info log when it clears, not on every poll.
  - `TestBroadcaster_EventAtTheBoundReachesTheClient` pushes an event of exactly the bound through `WriteEvent` and `NewReader`.
- **Log chunker (C1 carry-over):** `encodeLogBatches(entries, dropped)` splits into events of at most **500 entries and 1 MiB** each. An entry too large on its own is dropped and counted in `dropped`, and a loss is reported once, in the first batch.
  - Tests: order kept, nothing duplicated, both bounds, byte-identical to `Marshal(LogBatch)`, and reading through the client `Reader`.
  - **Its caller arrives with PR 2** (log relay). `golangci-lint`'s `unused` does not flag it, because the tests use it.
- A subscriber joining mid-outage gets the last snapshot **and** the current non-ok status, so old data is not shown as current. A subscriber of a healthy instance gets no initial status.

## 4. `server.go`

- **Before authentication**, the handler checks the method and the protocol header itself, so both answers are JSON rather than the mux's text/plain:
  - any method but `GET`/`HEAD` gets **405** with `Allow: GET, HEAD`;
  - any request without `Ember-Remote-Protocol: 1` gets **426** with `supportedProtocols: [1]`. A **missing** header is refused too (Q2).
  - The body is wrapped in `http.MaxBytesReader(…, 0)`.
- **After authentication** (the C2 middleware):
  - `/info` answers the handshake. Its capabilities are `snapshot` plus whatever `ServerConfig.Capabilities` adds.
  - `/config` and `/certificates` answer **404** with the JSON body `this daemon does not serve config` until PR 3. `TestServer_EveryRouteAnswersJSON` walks `routeScopes`.
- **`/stream`**, in order:
  1. Resolve the instance: without `?instance=` on a single-instance daemon, the default applies. On a multi-instance daemon, a missing `?instance=` gives 400 with `instances`, and an unknown one gives 404.
  2. `HEAD` answers the headers and returns **without taking a session**.
  3. A slot is reserved atomically under the registry lock. Beyond `MaxSessions` (16 by default) the answer is 503.
  4. Subscribe, send the SSE headers, `hello`, then the pending events, and a ping every 15 s without other traffic.
  - The session registry (`sessionId` → identity) is what PR 3 will check `Ember-Remote-Session` against.
- **Every write**, ping included, first revalidates the identity (C2's `Revalidate`). A removed, rotated or expired token, or a lost `snapshot` scope, closes the session as `revoked`. This follows your answer 7. Losing `logs` will only stop the log events, in PR 2.
- **Then a write deadline** of 10 s through `http.ResponseController`, and a flush.
  - Deadline exceeded → `slow_client`; any other write error → `client`.
  - If the deadline cannot be set, the session is **closed** (reason `client`) rather than run without protection. This cannot happen with `net/http`'s own writer.
- **Shutdown order**, stated in the `Server` doc for C4: close the `Broadcaster` first. Every stream then ends with `shutdown`, and `http.Server.Shutdown` returns, since it waits for active handlers. After `Close`, `Subscribe` refuses new streams with 503.
- `session.open` and `session.close` are audited with the § 6.5 keys. `events` and `bytes` count what `WriteEvent`/`WriteComment` returned. `ember_version` is read from an `ember/<version>` User-Agent.

## 8. Questions

1. **Status semantics.**
   - `unreachable` = the last poll failed. This mirrors `pollInstance`, which gets an error and stores nothing when `/metrics` fails.
   - `stale` = polls succeed, but the snapshot cannot be sent (too large or not encodable).
   - `ok` = the last snapshot was sent.
   - Unlike `/healthz`, there is no time-based `stale`: a hung poll ends in a fetch timeout, and so in `unreachable`.

   Do you accept these definitions? In particular: should a snapshot skipped for its size be signalled as `stale` (my choice, so the client does not freeze silently), or only logged?
2. **A missing `Ember-Remote-Protocol` header gives 426**, the same as a wrong one. It makes `curl` debugging slightly harder, but the client must always say which layout it expects. Acceptable?
3. **A 503 (session cap or shutdown) is not audited.** Should it be, as `remote.auth.denied` or as a new event?
4. **`hello` consumes a seq** from the shared counter, so every event carries a fresh, monotone id. `Last-Event-ID` is parsed at no point in C3: only the latest snapshot matters, and log resume comes with PR 2. Agreed?
5. **`HEAD /stream`** authenticates and resolves the instance, then answers 200 with the SSE headers and no body or session. Fine as a readiness probe for the client?
